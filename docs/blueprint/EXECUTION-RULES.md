# 执行守则 v3：质量第一、精准验证与自主脱困

> v2 由负责人 2026-11-16 批准，自 R2 起生效；v3 于 2026-11-17 按负责人“对成果足够高质量的追求为第一性原则，效率和成本仅作兼顾”的要求修订，自 R3 起生效（新增第 0 节、§2 第 11–17 条、第 5 节，修改 §1 与第 4 节）；R3 验收后补充 §2 第 18、19 条；R4-A 验收后补充 §2 第 20、21 条；R4-A.1 复验后补充 §2 第 22 条。由来与案例见 `LESSONS.md`。适用于实施方及其全部子代理，也约束规划方的验收方式。
> 与蓝图的关系：本守则替代蓝图中与之冲突的**验证与交付形式**要求（§13.3、§14.1 的收尾动作与证据包、各轮验收门里的数量与视口要求）；**不改变** 0.3 硬规则，也不改变 `SCOPE-TIERS.md` 中的“底线”。
> 由来：R1 约 35% 的时间花在自设的“零像素差”截图门上，7 次 CI 中 5 次因测试工具问题失败；端到端与截图工具代码多于产品前端代码。本守则的目标是验证成本至少减半，并让实施方遇到低性价比消耗时能**自己判断、自己脱困**，不必等负责人叫停。

## 0 质量第一

- 判断一项工作是否完成，只看一个问题：**用户（含汇报现场的领导）按计划里的方式使用时，能不能成功，结果对不对。**
- 精简验证减的是重复和过度（像素门、重复全量、证据包），**不减对用户成功的证明**（动作与结果断言、真实模型经界面、交叉角色、独立审查）。
- 预算是上限，不是目标。用时远低于预算不是优点；第 2 节第 9、10、17 条完成之前，不得以“提前完成”收口。

## 1 预算

- 每轮的预算由负责人在启动提示中写明（时长与额度占比，以先到者为准）；没写时按“一周额度的 35%”执行。实施方看不到额度时，以时长为准。
- 投入比例的参考：基础功能 ≥ 70%，验证 ≤ 25%，文档与汇报 ≤ 5%。
- **50% 检查点**：用掉**本轮预算**的一半时，在本轮计划“进展”节写 5 行以内：已完成、剩余、预计还需多少、准备降级或延后什么。写完继续执行，不等回复。
- **85% 收口线**：用到**本轮预算**的 85% 时，不再开新工作包，只把已开工的做到可交付，然后交付。收口时间里必须留出第 2 节第 17 条独立审查与第 10 条真实演练所需的时间，不能被新功能挤掉。

## 2 精简验证（至少减半）

1. **CI 是唯一的事实来源。** 本地只跑与改动相关的测试；后端全量回归只在合并进开发分支前跑一次，或交给 CI 跑。不在本地和 CI 上重复跑同一套全量。
2. **CI 分两层。** 推送触发“快速层”：代码检查、后端测试、前端单元测试、构建，目标 15 分钟以内。浏览器、截图、断网、升级演练归入“完整层”，手动触发，每轮最多 2 次（中途一次、交付一次）。
3. **截图只供审阅，不做像素比对门。** 每个新页面或改动页面 1 张，1366×768 一个视口；实施方逐张看过并在报告中列出发现的问题。三视口、两种视图、零容差比对都属于进阶。既有视觉基线因设计变更需要重拍时，在界面稳定后一次性重拍，用拼图（每张 12 图以内）审阅，基线与对比同一提交入库。
4. **端到端**：每个新页面一条主路径；越权与隔离用后端测试覆盖（底线）。
5. **不得自设高于规格的标准。** 规格没给数值的阈值，用工具默认值或常规值，并在报告里列出。规格写“不少于 N”的，做到 N 即可，不追加。
6. **证据**：不生成证据包，不逐图上传构件，不提交证据类文件；CI 保留一个汇总构件即可。
7. **报告**：一轮一份，按附录 F.2 十一节写要点，不超过两页。不写分包报告；中途不提交只改文档的“记录”类提交（进展随代码提交一起更新）。
8. **状态消息**：每 30–60 分钟一条，3 句以内，说做完了什么、在做什么、有没有阻碍。
9. **演示关键路径全覆盖**（R2 验收后补充）：本轮计划的主线、演练脚本（如 `R2-DEMO.md`）和验收门里点名的**每一个用户动作**，都要有一条自动化用例真正执行它，并断言结果（数据确实保存、状态确实变化、文件内容正确），不能只断言“请求成功”。精简验证减的是重复与过度，不减这一条。
10. **真实模型经界面**：涉及模型的主线，交付前必须用真实模型**通过浏览器界面**完整走通；汇报或演示用途的主线要求连续 3 次成功。接口脚本的真实模型演练不能代替。没有密钥时列入“待负责人执行”，不得声称已验证。
11. **界面泄漏扫描**（R3 起）：主线与新页面的端到端在简洁视图下扫描页面文字，不得出现内部字段名（如 `*_id`、`source_chunk_ids`）、英文状态标识、32 位编号、JSON 片段、ISO/UTC 原始时间。专业视图只允许在“技术详情”区域出现编号。
12. **前后端契约**（R3 起）：新增或修改的接口，前端请求体与响应用 `scripts/gen_api_types.py` 生成的类型，不手写对象结构；后端拒绝多余字段时，前端类型必须同样拒绝。
13. **真实模型早跑**（R3 起）：涉及模型的改动，在本轮进行到一半左右时先用真实模型经界面跑一次，尽早暴露模型输出与规则的不匹配；收尾时再按第 10 条连续跑。
14. **规格先成表**（R3 起）：规格密集的判定逻辑（核验、门禁、把握程度、权限组合等），实现前先把规格写成“应放行 / 应拦截”的正反例表（至少各 5 例），作为单元测试入库。
15. **交叉角色场景**（R3 起）：涉及权限、职责分离、审核的功能，至少有一条两人以上的交叉场景用例（如甲改写、乙采纳、甲审核被拒），覆盖新旧两个入口。
16. **诚实表述**（R3 起）：报告与回复中每一条“通过”都标明渠道（界面/接口/单元）、模型（模拟/真实）、环境（本地/CI）和对应提交号；没有执行的写“未执行”，部分通过的写清楚哪部分。
17. **交付前独立对抗审查**（R3 起）：交付前派 2–3 个新上下文的审查子代理，分别审查后端正确性与安全、前端与界面基准符合度、主线动作与演练脚本覆盖；只给它们代码与规格，不给自己的结论；确认属实的问题修复后再交付，审查发现与处理结果在报告第 9 节列一张表。子代理不用最高推理档，最多 5 个并行。
18. **快速层不可跳过**（R3 验收后补充）：快速层（代码检查、后端测试、前端单元、构建）在每一次代码推送上都运行。实施方可以为定向补验增加 CI 作业或提交标记，但标记只能**追加**作业，不得跳过或缩小快速层。交付提交上必须有一次全绿的快速层；完整层失败后的定向补验不能代替交付提交上的快速层。
19. **断言要能失败**（R3 验收后补充）：新写或修改的结构类、动作类断言，交付前用一个反例证明它会失败（例如故意把左边线偏移、把理由清空、让零值区块出现），在报告中列出反例。恒为真的断言等于没有断言。
20. **验收材料按真实写法准备**（R4-A 验收后补充）：演练与测试用的输入材料（制度、台账、问题）按真实业务的普通写法准备，不得加入实现所依赖的标签句、固定格式或关键词来让检查通过。计划点名的主线，除实施方自备的材料外，还要用规划方入库的“普通写法”材料走通；真实模型三连用规划方的材料。
21. **改既有入口必须对照旧操作**（R4-A 验收后补充）：凡是给既有入口加上新校验、门禁或守卫的工作包，动作清单必须包含旧页面上每个受影响的 0.7.0 操作（新建、修订后再发布、导入、审核）在新规则下仍能经界面完成。回归脚本与测试不得用直写数据库的办法满足新规则；确需改写既有回归的期望时，按“行为变化”逐条列入报告，不能只写“夹具已加强”。
22. **新写入口对照既有守卫**（R4-A.1 复验后补充）：凡新增或改道的写入路径（新能力、新按钮背后的接口、绕开旧接口直接调内核的代码），报告里列出它经过的每一道既有守卫——独立审核、受管技能、权责规范、专项、只读、机构隔离——并各有一条被拦住的用例。同一条规则在新旧入口必须由同一个函数判定，不能一边拦、一边不拦。系统自己推断出来的事实（从全文或引文里识别的日期、范围、条件、例外）不得标成“原文提取”，要单独标明并让核对人看得到。
23. **改共用测试助手先查调用方**（Windows 原生摸底后补充）：改写被多个脚本共用的测试助手、夹具或基线的期望之前，先列出它的全部调用方。同一个助手既操作当前版、又操作旧版基线（升级演练、旧版对照）时，期望按被操作的版本区分，不能只改成当前版的期望。改动波及本机跑不到的用例（Windows 原生、真实模型）时，报告里单列“已改未跑”，由规划方在验收时执行。

## 3 自主脱困

### 3.1 信号：出现任一项，立即做 3.2 的自检

| 编号 | 信号 |
|---|---|
| S1 | 同一项检查因测试工具或环境原因（不是产品缺陷）第 2 次失败 |
| S2 | 一项验证活动（写测试工具、调 CI、看图、跑全量）连续 30 分钟没有发现任何产品缺陷 |
| S3 | 一个工作包里新增的测试与工具代码，已经多于新增的产品代码 |
| S4 | 为同一个问题第 3 次触发完整 CI |
| S5 | 为了达到规格没有要求的精度（零像素差、比例恰为 1、精确计时）而反复修改 |
| S6 | 等待 CI 或长测试时只在轮询，没有并行推进别的工作 |
| S7 | 一个工作包里看图超过 10 张，或反复阅读同一份日志 |
| S8 | 被外部条件卡住（网络、密钥、平台权限），而重试不会改变条件 |

### 3.2 自检三问

1. 这项检查保护的是“底线”吗？
2. 如果把它降级或延后，负责人汇报或用户使用时会发现“某个功能没有或用不了”吗？
3. 再投入一小时，预期收益比把这一小时用在下一个“基础”功能上更大吗？

三问都答“否”，就按 3.3 自行降级，不必请示。

### 3.3 降级阶梯（从上往下选第一个可行的）

| 级 | 做法 | 需要请示吗 |
|---|---|---|
| D1 收窄 | 只跑失败的那一项；先在本地复现，再推 CI；不重跑全量 | 否 |
| D2 换法 | 换一种满足规格最低要求、更便宜的验证：功能断言代替像素比对，单元测试代替浏览器测试，工具默认阈值代替自设阈值 | 否 |
| D3 降为提示 | 把该检查改为不阻断，在 `STATUS.md`“降级与延后记录”登记一行：检查名、原因、恢复条件 | 否（底线类除外） |
| D4 延后 | 把该项移入进阶清单，继续下一个工作包 | 否（底线类除外） |
| D5 上报 | 只有涉及底线，且 D1–D4 都不适用时，停下请示：给出 2–3 个选项和推荐 | 是 |

S8（外部条件）直接走 D4 或 D5：能绕开的先做其余工作；绕不开且涉及底线的才上报。

### 3.4 红线：任何情况下不得降级

- 蓝图 0.3 硬规则与禁止事项清单。
- 既有测试与断言（附录 H.2 明确取消的除外）。
- 权限、机构隔离、只读边界、审计。
- 迁移无损、可重入、失败可恢复。
- 不伪造结果，不把模拟结果说成真实模型效果。
- 不推送发布分支，不打标签，不建拉取请求（除非负责人要求）。

### 3.5 记录

每次 D3、D4 只在 `STATUS.md` 的“降级与延后记录”表里写一行；轮末报告第 6 节汇总。不写长篇说明。

## 4 规划方的验收方式

- 默认做深入验收（R2 起的实践证明它能发现实施方自验漏掉的阻断问题），不以用时为目标。
- 必查：既有用例没有消失或变为跳过；发布分支、`requirements.txt`、既有流水线未被改动；没有密钥入库；底线类测试通过。
- 操作：按本轮计划的动作清单，用真实模型经浏览器亲自走一遍主线；用合成模型走一遍其余新路径。
- 材料与旧入口（R4-A 起）：除实施方的演练材料外，用规划方自备的普通写法材料亲自走一遍主线；对被改动的既有入口，亲自在旧页面做一次“修订后再发布”和一次“手工新建后提交”。
- Windows 原生（R4-B 起，R4-PLAN D23）：在交付代码上跑一次 Windows 原生流水线，逐个环节读结果，不只看总结论；流水线在第一个失败处停下，后面没跑到的环节如实记为未验证。触发方式是开一个草稿拉取请求、跑完即关，需要负责人授权。
- 审查：三路独立代码审查（后端、前端与界面、端到端与演练覆盖），关键结论逐条复核。
- 界面走查（R3 起）：对照 `docs/design/` 的界面基准与基准页，核对结构类断言结果，亲自看所有改动页面的 1366×768 截图。
- 发现问题列成清单交回，修复后只复验相关项。

## 5 界面基准（R3 起）

- `docs/design/UI-BASELINE.md`（界面基准规范）与 `docs/design/benchmarks/`（高保真基准页）是所有新页面和改动页面的上位依据；与蓝图第十部分冲突时以界面基准为准，冲突点已在 R3 计划“裁决”节列出。
- 所有页面只能使用统一页面骨架组件；功能目录里不得自写页面容器、页边距或最大宽度（由检查脚本强制）。
- 结构类可测断言（标题左边线一致、内容区之上横条数、首行数据位置、首屏字符数、页面字号种类）进入端到端，代替像素比对。
- 视觉细节（插图、动效、图标统一、登录页品牌表达、图表配色）仍属进阶，留待全站打磨。
