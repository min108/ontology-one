# 执行守则 v2：预算、精简验证与自主脱困

> 负责人 2026-11-16 批准，自 R2 起生效。适用于实施方及其全部子代理，也约束规划方的验收方式。
> 与蓝图的关系：本守则替代蓝图中与之冲突的**验证与交付形式**要求（§13.3、§14.1 的收尾动作与证据包、各轮验收门里的数量与视口要求）；**不改变** 0.3 硬规则，也不改变 `SCOPE-TIERS.md` 中的“底线”。
> 由来：R1 约 35% 的时间花在自设的“零像素差”截图门上，7 次 CI 中 5 次因测试工具问题失败；端到端与截图工具代码多于产品前端代码。本守则的目标是验证成本至少减半，并让实施方遇到低性价比消耗时能**自己判断、自己脱困**，不必等负责人叫停。

## 1 预算

- 每轮的预算由负责人在启动提示中写明（时长与额度占比，以先到者为准）；没写时按“一周额度的 35%”执行。实施方看不到额度时，以时长为准。
- 投入比例的参考：基础功能 ≥ 70%，验证 ≤ 25%，文档与汇报 ≤ 5%。
- **50% 检查点**：用掉**本轮预算**的一半时，在本轮计划“进展”节写 5 行以内：已完成、剩余、预计还需多少、准备降级或延后什么。写完继续执行，不等回复。
- **85% 收口线**：用到**本轮预算**的 85% 时，不再开新工作包，只把已开工的做到可交付，然后交付。

## 2 精简验证（至少减半）

1. **CI 是唯一的事实来源。** 本地只跑与改动相关的测试；后端全量回归只在合并进开发分支前跑一次，或交给 CI 跑。不在本地和 CI 上重复跑同一套全量。
2. **CI 分两层。** 推送触发“快速层”：代码检查、后端测试、前端单元测试、构建，目标 15 分钟以内。浏览器、截图、断网、升级演练归入“完整层”，手动触发，每轮最多 2 次（中途一次、交付一次）。
3. **截图只供审阅，不做像素比对门。** 每个新页面 1 张，1366×768 一个视口。三视口、两种视图、零容差比对都属于进阶。
4. **端到端**：每个新页面一条主路径；越权与隔离用后端测试覆盖（底线）。
5. **不得自设高于规格的标准。** 规格没给数值的阈值，用工具默认值或常规值，并在报告里列出。规格写“不少于 N”的，做到 N 即可，不追加。
6. **证据**：不生成证据包，不逐图上传构件，不提交证据类文件；CI 保留一个汇总构件即可。
7. **报告**：一轮一份，按附录 F.2 十一节写要点，不超过两页。不写分包报告；中途不提交只改文档的“记录”类提交（进展随代码提交一起更新）。
8. **状态消息**：每 30–60 分钟一条，3 句以内，说做完了什么、在做什么、有没有阻碍。

## 3 自主脱困

### 3.1 信号：出现任一项，立即做 3.2 的自检

| 编号 | 信号 |
|---|---|
| S1 | 同一项检查因测试工具或环境原因（不是产品缺陷）第 2 次失败 |
| S2 | 一项验证活动（写测试工具、调 CI、看图、跑全量）连续 30 分钟没有发现任何产品缺陷 |
| S3 | 一个工作包里新增的测试与工具代码，已经多于新增的产品代码 |
| S4 | 为同一个问题第 3 次触发完整 CI |
| S5 | 为了达到规格没有要求的精度（零像素差、比例恰为 1、精确计时）而反复修改 |
| S6 | 等待 CI 或长测试时只在轮询，没有并行推进别的工作 |
| S7 | 一个工作包里看图超过 10 张，或反复阅读同一份日志 |
| S8 | 被外部条件卡住（网络、密钥、平台权限），而重试不会改变条件 |

### 3.2 自检三问

1. 这项检查保护的是“底线”吗？
2. 如果把它降级或延后，负责人汇报或用户使用时会发现“某个功能没有或用不了”吗？
3. 再投入一小时，预期收益比把这一小时用在下一个“基础”功能上更大吗？

三问都答“否”，就按 3.3 自行降级，不必请示。

### 3.3 降级阶梯（从上往下选第一个可行的）

| 级 | 做法 | 需要请示吗 |
|---|---|---|
| D1 收窄 | 只跑失败的那一项；先在本地复现，再推 CI；不重跑全量 | 否 |
| D2 换法 | 换一种满足规格最低要求、更便宜的验证：功能断言代替像素比对，单元测试代替浏览器测试，工具默认阈值代替自设阈值 | 否 |
| D3 降为提示 | 把该检查改为不阻断，在 `STATUS.md`“降级与延后记录”登记一行：检查名、原因、恢复条件 | 否（底线类除外） |
| D4 延后 | 把该项移入进阶清单，继续下一个工作包 | 否（底线类除外） |
| D5 上报 | 只有涉及底线，且 D1–D4 都不适用时，停下请示：给出 2–3 个选项和推荐 | 是 |

S8（外部条件）直接走 D4 或 D5：能绕开的先做其余工作；绕不开且涉及底线的才上报。

### 3.4 红线：任何情况下不得降级

- 蓝图 0.3 硬规则与禁止事项清单。
- 既有测试与断言（附录 H.2 明确取消的除外）。
- 权限、机构隔离、只读边界、审计。
- 迁移无损、可重入、失败可恢复。
- 不伪造结果，不把模拟结果说成真实模型效果。
- 不推送发布分支，不打标签，不建拉取请求（除非负责人要求）。

### 3.5 记录

每次 D3、D4 只在 `STATUS.md` 的“降级与延后记录”表里写一行；轮末报告第 6 节汇总。不写长篇说明。

## 4 规划方的验收方式

- 以 CI 为准，加抽查和底线核对，目标 30 分钟以内。不再逐门全部重跑。
- 必查：既有用例没有消失或变为跳过；发布分支、`requirements.txt`、既有流水线未被改动；没有密钥入库；底线类测试通过。
- 抽查：每轮新功能挑 2–3 条主路径亲自走一遍。
- 发现问题列成清单交回，修复后只复验相关项。
