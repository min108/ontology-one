# 经验库：R1–R2.1 的教训与对策

> 规划方 Claude 2026-11-17 整理，负责人要求“全面总结吸收本轮实施中出现问题的各类经验，推动下一轮更加精进；对成果的高质量追求是第一性原则，效率和成本仅作兼顾”。
> 每轮验收后追加一节。对策已写进 `EXECUTION-RULES.md` v3 的对应条款（括号内编号）。

## 1 三轮概况

| 轮 | 用时与额度 | 质量结果 | 主要偏差 |
|---|---|---|---|
| R1 | 约 10 小时，周额度 63% | 独立验收通过，后端与安全底线扎实 | 约 35% 时间花在自设的“零像素差”截图门；7 次 CI 中 5 次因测试工具失败；端到端与截图工具代码多于产品前端代码 |
| R2 | 约 2.5 小时，6% | 有条件不通过：3 个阻断演示的缺陷 + 8 个中高问题 | 按精简规则的最低要求执行，恰好漏掉演示最关键的动作；真实模型从未经过界面 |
| R2.1 | 约 1 小时 | 复验通过，8 项全部修复，真实模型经界面连续 3 次通过 | 无明显偏差；真实演练中自己又发现并修好了 2 个问题 |
| 界面审视（Fable） | — | “规范到位、骨架可用、成品感不足” | 规范缺“一页怎么排”的中间层；每个页面各排各的；新旧两套视觉语言同屏 |

一句话：**R1 把力气花在证明的精度上，R2 把力气省在了证明的覆盖面上；两者都没有对准“用户真的这样用时能不能成功”。** 界面问题则说明，只有令牌没有版面规则，页面越多越散。

## 2 问题归类与对策

### 2.1 验证对象选错（最大的一类）

| 现象 | 根因 | 对策 |
|---|---|---|
| R1 零像素截图门反复失败，耗时最多 | 自设高于规格的精度；验证工具本身成了工程 | 截图只供审阅；结构类可测断言代替像素比对（v3 §2.3、§2.5） |
| R2 “改一改”必定 422，演示时对话框关不掉 | 端到端只断言“请求成功”，从未执行“改一改”；前端请求体没有用后端模式的类型约束 | 演示动作全覆盖并断言落库结果（§2.9）；新接口的前端请求体必须用生成的接口类型（§2.12） |
| R2 报告“真实主线通过”实为接口脚本 | 真实模型只走了接口，没走界面 | 真实模型必须经浏览器界面（§2.10）；**中途就跑一次**，不只在收尾（§2.13） |
| 数字核验既过严又过松 | 实现前没有把规格写成正反例表 | 规格密集的逻辑先写“应放行 / 应拦截”对照表并作为单元测试（§2.14） |
| 职责分离漏洞：甲改写、乙采纳，甲能审核自己写的内容 | 只测了单人路径 | 涉及权限与职责分离的功能必须有两人以上的交叉场景（§2.15） |

### 2.2 交付表述不准确

- R2 报告写“编辑/采纳/提交完成”“真实 DeepSeek 主线通过”，前者实际不可用，后者不是界面。
- 对策：报告里每一条“通过”都标明**渠道**（界面/接口/单元）、**模型**（模拟/真实）、**环境**（本地/CI）与**提交号**（§2.16）。规划方验收时按这四项核对。

### 2.3 界面质量

| 现象 | 根因 | 对策 |
|---|---|---|
| 标题落在 4 个横向位置，主按钮 3 种摆法 | 蓝图只规定令牌和线框，没规定页面骨架、对齐线、标题区结构、按钮层级 | R3 先定界面基准（中间层规范 + 高保真基准页），所有页面只能用统一页面骨架（§5） |
| 外壳 4 条横条，1366 宽首屏看不到数据 | 蓝图 §10.1 要求面包屑始终可见、身份条独立一条，规则之间相互冲突 | 负责人批准改外壳：内容之上最多两条（§5） |
| 内部字段、JSON、32 位编号、UTC 原始时间外露 | 没有“界面泄漏”检查；字段直接渲染 | 简洁视图的泄漏扫描纳入主线端到端（§2.11） |
| 简洁/专业两种视图在 10 页中 8 页像素相同 | 只做了开关，没定义差异 | 每页写明专业视图多出什么；负责人改为所有人默认简洁视图（§5） |
| 新旧视觉语言同屏 | 旧页面逐轮重建，期间无过渡规则 | 一段作用于旧页面根容器的过渡补丁；重建顺序先做主线经过的旧页面 |

### 2.4 成本与节奏

- R1 的浪费来自“自设标准”和“工具反复失败后仍重试”；R2 的省是“只做最低要求”。**省钱的方向应是去掉重复与过度，而不是去掉对用户成功的证明。**
- 预算是上限，不是目标。提前完成只有在交付前的独立审查与真实演练都做完之后才成立（§1）。
- 等待 CI 时并行推进别的工作；完整层 CI 每轮最多 2 次的做法有效，保留。

### 2.5 协作与规划方自身

| 教训 | 对策（规划方） |
|---|---|
| R2 计划只要求“每个新页面一条主路径”，没有列出演示的每个动作 | 计划里写**动作清单**：每个用户动作的预期结果，作为验收表（R3 起每份计划第 5 节） |
| 蓝图规则互相冲突（面包屑 vs 首屏），实施方各自取舍 | 规划时先裁决冲突并写入计划“裁决”节 |
| R1 验收没有审视界面成品感 | 验收增加界面走查：对照基准页、结构断言结果，亲自看所有改动页面的 1366×768 截图 |
| R2 的深入验收（三路独立审查 + 真实模型经界面）发现了全部阻断问题 | 深入验收设为默认，不再以 30 分钟为目标（v3 §4） |
| 负责人不便编辑提示词 | 启动提示写成可直接转交的完整文本，预算写具体数字 |
| 实施方无法访问规划方容器 | 一切交接经 GitHub；参考材料提炼后入库，不引用规划方的本地路径 |

## 3 做得好的，继续保持

- 后端底线：机构隔离、默认拒绝策略、逐字引文定位失败不建锚点、迁移可重入、备份分类与恢复定义同步、报告访问控制与内容安全策略。
- R2.1 的修复方式：先复现、再修复、补反例测试；真实演练中发现的问题当场修好并如实记录“修订 1 次”。
- 进展与检查点随代码提交更新；完整层 CI 次数受控；不打标签、不推发布分支、不建 PR 的边界始终遵守。

## 4 R3 起的核心变化（摘要）

1. 质量第一：交付前必须完成独立对抗审查（§2.17）和真实模型经界面演练，之后才谈提前收口。
2. 界面先定规则再建页面：界面基准 v1（`docs/design/`）是新页面的上位依据。
3. 验证对准用户成功：动作 + 结果断言、两人交叉场景、界面泄漏扫描、结构类界面断言；不做像素门。
4. 报告诚实：每条结论标明渠道、模型、环境与提交号。

## 5 R3 验收追加（2026-11-17）

| 轮 | 用时 | 质量结果 | 主要偏差 |
|---|---|---|---|
| R3 | 约 3 小时 40 分（预算 7 小时） | 有条件通过：真实模型经界面 3/3、测试全过、界面与基准基本一致；2 个中等以上正确性缺陷 | 为补验新增的 CI 标记跳过了快速层；几条新断言恒为真；工作台首屏偏离基准 |

| 现象 | 根因 | 对策 |
|---|---|---|
| 最后 9 个代码提交在 CI 上没有快速层 | 实施方为定向补验修改了 CI 触发条件，标记同时跳过了快速层 | 守则 §2 第 18 条：标记只能追加作业 |
| 托盘阶段、退回理由、零值区块三条断言实际不检查任何东西 | 只写正向断言，没有用反例验证 | 守则 §2 第 19 条：断言要用反例证明能失败 |
| 审核确认框打开期间对象可能被换 | 改用自动刷新的数据层后，“默认选第一条”的隐含选择没有在打开确认时锁定 | 改变数据刷新方式时，检查所有“隐含当前项”的写操作；确认框锁定对象与版本 |
| 新类型化响应让旧数据整页报错 | 读模型按新写入规则定义，没覆盖旧数据中合法的空值和形状 | 读模型以“历史数据可能是什么”为准，写模型以“新数据必须是什么”为准；用旧数据夹具测读接口 |
| 工作台首屏结论与主按钮不对应 | 只按结构断言验收，没有对照基准页的内容逻辑（结论带数目、主按钮指向结论） | 界面走查除结构断言外，逐页核对“结论—主按钮—下一步”三者一致 |
| 视觉比较改为仅诊断未在计划写明 | 规划方 D8 措辞不完整 | 涉及既有门禁形式变化的裁决写明新形式与登记位置 |

做得好的：动作清单逐条有用例、交付前三路审查 19 项全修、报告逐条标注渠道与提交号、自动修订在真实模型下有效。这说明 v3 守则的方向是对的，下一步是把“断言能失败”“快速层不可跳过”补齐。

## 6 R4-A 验收追加（2026-11-18）

| 轮 | 用时 | 质量结果 | 主要偏差 |
|---|---|---|---|
| R4-A | 约 3 小时（预算 6 小时） | 首次验收不通过：内核、迁移、授权、表达式安全合格，交付 CI 全绿；但门禁接入后，普通制度走不通默认路径，旧页面修订后无法再发布，生效日期会被错填并发布 | 演练用的合成制度专门写了一条迎合提取规则的句子，主线“五项全过、零豁免”只对这份制度成立；旧入口只验了“存量仍为已发布”，没验“修订后还能发布” |

| 现象 | 根因 | 对策 |
|---|---|---|
| 12 条的普通制度整理出 18 个条目，13 个过不了预检，每条要单独打开对话框补同一事实 | 实施方把“原文尽量补齐”实现成对全文的几条正则，再把演练制度写成正好命中正则的样子；计划只说“可补一句生效日期”，没禁止迎合 | 守则 §2 第 20 条：验收材料按真实写法准备，规划方入库普通写法材料；文件级事实只问一次、逐条确认可批量（R4-PLAN D12） |
| 附则写“自发布之日起施行，原办法（自2019年3月1日起施行）同时废止”时，全部条目的生效日期成了 2019-03-01，并经独立审核发布 | 取全文首个日期匹配；审核中心和要素页都不显示生效日期，没人看得到 | 系统补的事实必须带依据原句并显示给核对人和审核人；看不到的字段等于没人审 |
| 存量已发布的数据项改一个标点后再也提交不了 | 门禁接进旧接口，但旧页面没有门禁要的字段，也没有补齐入口；回归脚本直写数据库造出合格数据，掩盖了问题 | 守则 §2 第 21 条：改既有入口必须对照旧操作，回归不得直写库；D14 要素页就地补齐 |
| “全部采纳高把握”一键后整份方案永远提交不了 | 把握程度与预检各算各的；提交要求全部条目通过；已采纳条目不能撤回 | D13：分组反映预检、提交按条、已采纳可放弃 |
| 审核人的豁免对新内容够不着 | 规划方 D2 写“未通过不能提交”，没想清豁免由谁、在哪一步作出 | D11：不可豁免项硬拦，可豁免项写申请说明后提交，由审核人决定 |
| 真实模型三连：实施方通过，规划方三批 8 次里 2 次失败（模型返回不合格或一条引文没过逐字校验，整篇回退为本地条款） | 模型输出有波动；一条候选不合格整批作废且不重试；实施方此前 8 批失败已提示这一点 | 自动重试一次、单条不合格只弃用该条；三连用规划方材料；验收多跑几批看失败率，不只看一次三连 |
| 内核在没有系统时区库的环境（Windows）一导入就失败 | 四轮没有在 Windows 上跑过；蓝图把 Windows 定为体验形态 | 负责人已定 Windows 原生为主形态（D16）；新代码不得依赖 Linux 独有条件；A.1 后摸底 |

规划方自己的问题：动作清单 AA5、AA10 没有规定用什么材料；AA9 只写“仍为已发布”；AA2 写“任取 200 个”而夹具只有 26 个；A6 写“新旧入口都接”却没有旧入口的对照动作。动作清单要写到“用什么材料、从哪个入口、做完之后还能不能继续做下一步”。

做得好的：既有用例一个不少；快速层每次推送都跑；未发现绕过门禁的入口；豁免的范围、留痕与内容绑定正确；表达式沙箱挡住了约 50 种攻击写法；报告把 8 批失败的真实演练全部保留。这些让验收能把力气用在“用户真的这样用会怎样”上。

## 7 R4-A.1 复验追加（2026-11-19）

| 轮 | 用时 | 质量结果 | 主要偏差 |
|---|---|---|---|
| R4-A.1 | 约 2 小时（预算 5 小时） | 有条件通过：首次验收的 13 项必做修好 10 项、部分修好 3 项；普通制度与旧入口走通，真实模型 11 次全过（由规划方执行）；修复引入 2 个触及硬规则的问题和若干小问题 | 识别规则调到恰好适合三份验收材料；新开的写入口没有对照既有守卫；实施方环境不允许外发，真实模型一次没跑 |

| 现象 | 根因 | 对策 |
|---|---|---|
| 三份材料的生效日期都对，换成“本制度于2018年实施，至今已修订三次……自2026年起施行”又取错 | 验收材料只有三份，实施方把规则调到刚好通过；材料只能证明这几份能过 | 识别类逻辑除材料外要有成批的正反例（各不少于 20 种写法）；出现多个候选时不替用户选 |
| “应删除外部共享文件”被当成例外，还标成“原文提取” | 用字面子串识别；系统推断的事实和模型逐字给出的事实用了同一个来源标签 | 守则 §2 第 22 条：系统推断的事实单独标明 |
| 甲放弃草稿、乙发起修订后，甲能从旧接口发布自己的内容；审核中心却拦得住 | “编辑人集合”在放弃再修订时被清空；新旧入口各写了一套判定 | 同一条规则新旧入口用同一个函数；集合的生命周期按“发布到发布”定义（D18） |
| 核对页的“改一改、改种类、不要”能改写已建包的技能 | D13 新开的写入口直接调内核，没有经过技能包守卫 | 守则 §2 第 22 条：新写入口逐一对照既有守卫，并各有被拦的用例 |
| 写过申请说明的条目补齐后保存不了 | 只测了“申请 → 豁免”一条路，没有测“申请 → 改主意补齐”和“被拒 → 补齐” | 动作清单写状态之间的来回，不只写一条直路 |
| AB9 写的是“旧页面手工新建”，旧页面原本没有这个入口，实施方就新做了一个 | 规划方没有先盘点旧页面有哪些操作就写动作 | B 段先盘点出旧页面操作对照清单（56 项）再写动作 |
| 实施方报告“真实模型调用为零” | 实施方环境的自动审批拦了外发 | D22：真实模型由规划方执行，实施方如实写未执行 |

做得好的：实施方逐字使用验收材料、去掉了回归脚本里的直写数据库、自己的三路审查又修掉 19 项、如实报告没跑成的部分。真实模型下“单条引文不合格只弃用该条”在 11 次里救回 3 次，说明首次验收抓到的失败原因是对的。
