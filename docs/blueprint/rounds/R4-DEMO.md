# R4 制度核对、机构发布与检索演练（1.3.0）

## 从原制度检索

1. 用建设人员交入 `regulation-plain.txt`，读取原件、核对条目后提交。另一名审核人员查阅出处并发布。回到顶部搜索框输入 `10个工作日`，在前五项中打开已发布规则，查第四条原句、办理时限及审批资料。
2. 输入 `一次性告知经办部门补正`。先打开引用这句话的规则，再从同一批结果打开“制度原文片段”，核对原文页中高亮的条款。按规则名称、编号或已登记且重新发布的别名检索，可以回到同一要素。
3. 用查阅人员搜索一条草稿，再用建设人员搜索同一名称，比较可见结果和状态。用维护页搜索框查 `预付款比例`，与顶部检索在相同资产范围内的排序逐条核对。
4. 机构管理员可向 `POST /api/v2/system/search-index:rebuild` 提交空 JSON 对象。用返回的任务编号访问 `GET /api/jobs/{job_id}`，完成后重复上述检索。在线重建保留原件、审核与发布记录。

合成模型的浏览器演练会从原件开始，办理五项独立发布，执行 S1–S12，并在回执中记录原句、排序和后台任务。用 `--benchmark` 另行启动一次 BA12，演练会在同一临时机构补足一万条要素后记录连续 200 次调用的全部耗时。 [原件与检索预期](r4b-materials/README.md)

```sh
python e2e/run_r4.py --grep 'R4-B BA7' --output work/r4b-demo/search
```

## 公共部分的发布版本

要素在机构内独立审核发布后即可使用。机构公共部分的发布版本保存某一时点的成员、关联和引用，供核对组成以及随后变更的范围。以下操作需要已登录的机构库、会话 CSRF 与当前工作区请求头。

1. 机构管理员或已指定的建模师负责人，向 `POST /api/v2/capabilities/release.create_draft:invoke` 传入 `{"module_id":"MOD-DEFAULT"}`。按返回的条目、门禁、差异及建议版本号核对。首次版本是 `1.0.0`。
2. 以返回的 `id` 作为 `release_id` 调用 `release.submit`。另一名有审核权的人员调用 `release.publish`。如要求后台冻结，在本次审核请求中加 `"background":true`，用返回的任务编号跟踪。审核会话失效时重新登录、核对并办理。
3. 用 `GET /api/v2/releases/{release_id}` 读取实际快照、版本、审核人和清单哈希。只改文字、增加资产、归档资产后，可分别核对修订、次和主版本建议。撤回最新版本后再读 `GET /api/v2/modules/MOD-DEFAULT` 核对当前指针，并从历史版本读回原快照。

在专用 MySQL 测试实例中，设置 `RUN_JOBS_MYSQL_TESTS=1` 和该实例的 `MYSQL_*` 连接参数后，可运行下列两组动作。演练使用独立机构数据，旧备份来自已验收的 0.7.0 版本。

```sh
.venv/bin/python -m unittest tests.migrations.test_r4b1 -v
.venv/bin/python -m unittest tests.r4b.test_release_actions -v
```

沿用 R3 演练的隔离 Compose 环境与建设、审核、分析三个身份。启动入口为 `scripts/start_r2_demo.py`。本轮使用规划方提供的三份原文。测试回执注明实际渠道和模型。 [环境与账号](R3-DEMO.md) · [验收材料](r4a1-materials/README.md)

## 上传到报告

1. 建设人员在工作台拖入 `regulation-plain.txt`，点“开始整理”。核对页顶部应显示 **2026-01-01**，依据是第十二条“本办法自2026年1月1日起施行”。查看整理结果中的自动重试和弃用数。若整篇回退，页面显示“本次未经 AI 整理”，本次真实模型演练计失败。
2. 核对第四条的原文、适用范围与条件。打开顶部批量确认清单，逐条读直接显示的依据原句，再勾选自己已经核实的条目。条件和例外分别选择。第五条的补正要求来自该条原文，即使手工清空该值，仍须逐条核对。遇到多处施行日期或附件引述时，先在文件顶部核对候选原句，再选择适用于本次发布的日期。适用主体在“改一改”中选择。
3. 点“全部采纳高把握”。查看“还需补充”中的逐项原因。核实数据项的单位和记录粒度后填写；错误归入技能的制度条款可改为规则，确属技能的去技能工作台完善。已采纳的草稿也可点“不要”。确认提交框中的可送审数与留存数，再提交。
4. 独立审核人员在审核中心打开该规则，核对范围、条件、例外、生效日期、适用主体及各项来源。发布确认框应再次显示生效日期。回到已发布要素，点“就此提问”，询问本条规定的办理时限和申请材料。
5. 生成报告，点击出处上标核对引文和高亮。下载 Word 和离线网页，确认第四条的“10个工作日”及单位均保留。

分别上传 `regulation-repeal.txt` 和 `regulation-history.txt`。两份的日期初始均应为空。前者的 2019-03-01 属于废止的旧办法，后者的 2018-05-01 属于预算管理历史。浏览器演练将 **2026-11-18** 作为另行给定的模拟发布或印发日，在顶部填写一次。核对日期来源为“核对人填写”。差旅报销第三条的时限应为 **15个工作日**。 [原文与预期](r4a1-materials/README.md)

## 从旧页修订

用原资产页修订 0.7.0 数据项或知识、从原审批规则页修订授权规则。受拦时点“去补齐”，定位五项检查中缺失的字段。手工内容缺可定位原件时，建设人员可为该项写明原因后送审。审核人员必须逐项填写接受理由或退回理由。本轮全部编辑人和提交人均由其他审核人员办理。发布后核对原编号、版本、日期以及动态中的申请与办理记录。

在旧素材页点候选的“采纳为草稿”，从原页面提交审核，由另一人通过并发布。旧数据资产页可下载标准模板，填入数据项编号、业务含义、单位和粒度，选“Excel 一键导入”。在导入的每条数据项中核对行出处、单位和粒度，再走相同的发布流程。权责规范仍从原审批规则页新建。升级前已审核通过的条目可直接从旧页发布。

若模型给出的候选引文无法定位，到核对页查看“以下原文没有形成条目”，读完原文可将该段保留为待核对条目。已采纳的条目点“不要”会先要求确认。补齐原先申请豁免的缺项后，可在动态中核对撤回记录；没有申请过的条目，动态中应没有豁免事项。

## 自动复现

在有建库权限的一次性 MySQL 8.4、Node 22 和 Chromium 环境运行。每次使用新的输出目录，真实模型密钥由运行环境提供给 `DEEPSEEK_API_KEY`。

```bash
# 合成模型。包含原 R3、R4 动作、普通制度、旧页修订与导出
.venv/bin/python e2e/run_r4.py --output work/r4a1-demo/actions

# 真实模型。首次贯通一次、三份原文分开记录
.venv/bin/python e2e/run_r4.py --live --repetitions 1 --material regulation-plain --output work/r4a1-demo/early
.venv/bin/python e2e/run_r4.py --live --repetitions 1 --material regulation-repeal --output work/r4a1-demo/repeal
.venv/bin/python e2e/run_r4.py --live --repetitions 1 --material regulation-history --output work/r4a1-demo/history
.venv/bin/python e2e/run_r4.py --live --repetitions 3 --material regulation-plain --output work/r4a1-demo/final
```

`runner.json` 记录代码提交、模型与接口地址、实际提炼结果、人工操作、送审数、逐项发布检查、报告校验及资源清理。连续三次使用三个全新数据库，第一遍失败即停止。AA2 的 200 条为 24 条原件与 176 条合成副本，AB16 另查原文片段在页面中的起止位置。 [交付报告](R4-REPORT.md)
