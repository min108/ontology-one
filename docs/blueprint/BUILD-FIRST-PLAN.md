# 功能优先实施计划

> 负责人 2026-11-19 决定：调整开发顺序——先把目标功能全部做出来，看到成品立起样子，再集中做测试、修缺陷和打磨。本文件由规划方据此制定，自即日起生效。与 `EXECUTION-RULES.md`、各轮计划冲突之处，建设期内以本文件为准。

## 1 两个阶段

| 阶段 | 做什么 | 什么时候结束 |
|---|---|---|
| **建设期** | 按路线把全部“基础”功能做出来，每一项都能在界面上走通 | 第 4 节的 8 轮做完 |
| **打磨期** | 对成品做一次全面体检，按轻重修掉待办清单里的问题，再做 Windows 收敛、界面打磨和发布准备 | 总验收通过 |

建设期产出的版本**只用于演示和内部查看，不接真实用户和真实数据**：已知的安全漏洞（例如有人可以审核自己写的内容）要到打磨期才修。

## 2 建设期的目标与“做完”的标准

目标只有一个：功能齐全、能看、能点、能走通。

一项功能算“做完”，要同时满足三条：

1. 从导航或上一步能进得去，页面打得开；
2. 按正常用法走一遍主路径，数据存得住，下一步接得上；
3. 交付说明里写清楚“从哪里点、点什么、会看到什么”。

先铺开、后做深：一轮里列出的功能要先全部做到上面三条，有余力再做细节。

## 3 建设期的规矩

### 3.1 保留的少数规矩

这几条事后补不了，或者不守就盖不下去，建设期照常执行：

1. **不丢数据、能升级。** 表结构变化走迁移；`entities` 12 列、`relations` 7 列不变；备份分类与恢复定义同步。
2. **不拆还没有替代品的旧功能。** 新页面做好后成为默认入口，旧页面留作“旧版入口”，到打磨期核对无误后再删除。
3. **既有自动测试保持通过。** 每次推送的快速层必须全绿（它在 GitHub 上自动运行）。新功能有意改变了旧行为时可以改写旧用例的期望，在交付说明里各写一行；不删除既有用例。
4. **新读写走统一入口。** 权限、机构隔离、可见性、写入内核、能力登记这些已有的统一入口，新代码一律经过它们，不另开旁路。这是施工规矩，不是为了本轮测试。
5. **仓库安全照旧。** 密钥不入库；不改 `requirements.txt` 和两条受保护流水线；不推发布分支、不打标签、不建拉取请求。
6. **不依赖 Linux 独有的条件**（平台将以 Windows 原生为主形态）。
7. **不把模拟结果说成真实结果。** 交付说明如实写明哪些走通了、哪些没做、哪些是已知毛病。

### 3.2 暂停的做法

以下做法建设期一律暂停，打磨期再恢复：

- 交付前的三路独立审查；
- “用反例证明断言能失败”和各类测试数量门槛；
- 每个动作逐条写自动化用例——改为**每个新页面或新能力一条主路径用例**；
- 真实模型连续三次——改为规划方每轮用真实模型走一遍主线；
- 逐条的“行为变化清单”“改写断言清单”“守卫对照表”；
- 完整层 CI 作为交付门——改为每轮交付时跑一次作参考，失败项记入待办，不为此返工（主路径断了的除外）；
- 规划方的深度验收——改为第 3.4 节的轻查；
- Windows 原生流水线、视觉基线比对、性能测量。

### 3.3 发现问题怎么办

所有已知问题集中记在 `BACKLOG.md`（待办清单），按四级分类：甲（上线前必修：安全、铁律、数据对错）、乙（影响演示观感）、丙（体验与细节）、丁（测试与工程）。

建设期内只在两种情况下动手修：

- **挡路**：不修就没法接着做下一项功能，或者新功能的主路径走不通；
- **顺手**：正好在改这块代码，半小时内能修好。

这两种情况修完在交付说明里提一句即可，不单独验证。其余问题一律记入待办，不停工。

### 3.4 节奏

- **交付即启动下一轮。** 实施方交付后，负责人可以立即转交下一轮的启动提示，不必等规划方查完。规划方提前写好下一轮的启动提示。
- **规划方轻查，不阻塞。** 每轮交付后规划方只做四件事：核对快速层结果；用真实模型把新主线走一遍；给负责人一组截图看成品的样子；把发现的问题记入待办。不派审查子代理，不在本地重跑全量测试。
- **只有一种情况叫停**：上一轮的主路径断了，下一轮没法接着盖。此时规划方立即告知负责人，由实施方在当轮内先修。

### 3.5 预算与交付物

- 每轮时长不超过 7 小时，额度不超过本周额度的 25%，以先到者为准；用到 85% 起不再开新功能。
- 交付物精简为三样：代码；**一页交付说明**（做了什么、从哪里看、没做的、已知毛病）；同步 `AGENTS.md` 的代码地图和 `STATUS.md` 的一行进度。不再写长篇报告和证据附录。

## 4 建设期路线（8 轮）

功能范围仍以蓝图任务书和 `SCOPE-TIERS.md` 的“基础”为准；“进阶”一律不做。

| 建设轮 | 版本 | 做什么 | 做完后能看到什么 |
|---|---|---|---|
| 1（R4-B 下） | 1.3.0 | 本体目录补齐、统一要素页、知识专栏、机构本体页与发布版本界面、可见范围与敏感级别、查阅者与分析者账户 | 所有内容在一个目录里查；点开任何一条都是同一种页面，能看能改；能把一批已发布内容打成一个版本 |
| 2（R5） | 1.4.0 | 实例层（数据绑定、对象查询、规则与指标执行）、图谱 2.0、演示机构与演示数据 | 规则和指标在台账数据上算出结果；新的图谱；一键装载的演示机构 |
| 3（R6） | 1.5.0 | 建设主线补齐：素材中心、台账接入、万能入口与工作台 v2、核对页补齐、场景工作室五步 | 拖进一份文件就知道下一步做什么；一个业务场景按五步走通 |
| 4（R7） | 1.6.0 | 智能体平台：助手底座、工具目录与确认分级、后台运行与续跑、助手界面 | 助手能在后台办事、能续跑，每一步写操作都要确认 |
| 5（R8） | 1.7.0 | 建设助手、场景向导、访谈、技能、权责三类工作台 | 用对话完成建设；从访谈整理经验；技能从起草到复测 |
| 6（R9） | 1.8.0 | 应用助手、分析计算、成果引擎（网页、Word、Excel）、成果库 | 提问得到带依据的回答；生成可下载的报告并入库 |

每轮开工前，规划方把该轮的功能清单和“做完后能看到什么”写成启动提示。

## 5 打磨期

| 步骤 | 做什么 |
|---|---|
| 1 全面体检 | 对成品做一次完整的安全与正确性审查和全流程走查；新发现的问题并入待办并排序 |
| 2 分批修复 | 先甲类，再乙类、丙类；每批修完由规划方复验，恢复反例、独立审查等做法 |
| 3 收敛 | Windows 原生收敛与流水线、升级与备份恢复演练、旧页面清除 |
| 4 发布准备 | 界面打磨、性能、离线部署包、单点登录、文档、总验收 |

`EXECUTION-RULES.md` 的全部规则在打磨期恢复执行。

## 6 这样做的代价与对策

| 代价 | 对策 |
|---|---|
| 问题会越攒越多，打磨期的工作量不会小（规划方估计相当于三到四轮建设，这是估计） | 所有问题当场记入待办并分级；打磨期先体检、再按轻重修 |
| 地基上的毛病如果很晚才发现，返工大 | 3.1 的规矩照常执行；规划方每轮轻查，发现主路径断了立即叫停 |
| 建设期的版本有已知安全漏洞 | 只用于演示和内部查看，不接真实用户和真实数据 |
| 既有测试被新功能冲掉 | 快速层必须全绿；不删除既有用例 |
